# Context and Conventions

Read this alongside `PROJECT_OVERVIEW.md` (why this repo exists, branch model) and
`PLAN_3_MAXIMUM.md` (the authoritative design). This file holds the operational knowledge a new
session needs in order to pick the work up without rediscovering it: environment quirks, the coding
conventions the final design must follow, and where each branch currently stands.

---

## 1. Coding conventions

These apply to all new and refactored code.

### Naming

| Kind | Style | Example |
|---|---|---|
| Constants (`static final`) | `SCREAMING_SNAKE_CASE` | `GOAL_X_METERS`, `TUNING_MODE` |
| Enum constants | `SCREAMING_SNAKE_CASE` | `IDLE`, `SPINNING_UP`, `WAITING_FOR_TURRET` |
| Classes, interfaces, enums, records | `UpperCamelCase` | `ShootingSolver`, `TurretIOTalonFX` |
| Methods | `lowerCamelCase` | `solveStationary`, `getEstimatedPose` |
| Fields and local variables | `lowerCamelCase` | `lastResidualSec`, `virtualGoal` |

### Documentation

**Every method carries a permanent documentation block**: a description, an input list (`@param`),
and an output list (`@return`, or an explicit `<p><b>Outputs:</b>` note for `void` methods naming
what it writes and what hardware it commands).

**Implementation notes are kept separate from documentation.** When a skeleton method is
implemented, the body opens with an `IMPLEMENTATION (was TODO: "...")` comment quoting the original
TODO and explaining how the implementation satisfies it and why the approach was chosen. The Javadoc
survives implementation; the `// TODO:` inside the body is deleted once the work is done.

Comments should explain *why*, and especially should call out the failure mode a piece of code
prevents — that is the part a reader cannot reconstruct from the code itself.

### Other standing rules

- **All constants live in `Constants.java`** — as `LoggedTunableNumber` when they might need
  changing at a competition, as plain `static final` when physically fixed (gear ratio, CAN ID).
- **Never guess field- or game-dependent values.** Anything depending on the REBUILT field carries
  a `TODO: MEASURE` naming where the number comes from.
- **Units are meters, radians, seconds**, except motor speeds in RPM where that is the natural
  tuning unit. Any field whose unit is not obvious carries it in the name.
- Spotless with `googleJavaFormat` runs automatically on `compileJava`: 2-space indent, 100-column
  limit, and unused imports are stripped.

## 2. Outstanding: the constants naming migration

**The existing code does not follow the constants convention above.** It currently uses the WPILib
`k`-prefix style (`kGoalXMeters`, `kTuningMode`, `kMaxSolverIterations`). Converting to
`SCREAMING_SNAKE_CASE` is real, un-started work.

Measured scope, as of this file being written:

| Location | Declarations | Note |
|---|---|---|
| `Constants.java` | 176 when this was counted; M10 added a `Superstructure` block plus three `Field` and `Vision` entries | rename these |
| `RobotState.java` | 1 | `kBufferSeconds`; rename |
| `generated/TunerConstants.java` | 51 | **do not rename** — see below |
| References tree-wide | ~760 | all must be updated with the declarations |

**`TunerConstants.java` is generated by CTRE Tuner X.** Renaming its constants would be silently
reverted the next time anyone regenerates the swerve project, and the regeneration would then fail
to compile against the renamed references. Leave that file in its generated style and accept the
inconsistency at that one boundary, or wrap the values behind hand-written aliases in
`Constants.java`.

Suggested approach: do it as its **own branch with no other changes**, so the diff is purely
mechanical and reviewable, and so it cannot collide with in-flight feature work. Rename declarations
and references together, then `./gradlew compileJava && ./gradlew test` — the compiler catches every
missed reference, and the 24 unit tests catch any that silently resolved to the wrong symbol.

Also note the enum constants **already** comply, and classes, methods, fields and locals already
comply. Only constants need changing.

## 3. Environment: what does and does not work

These cost real time to rediscover.

**The Claude Code agent runs inside a snap sandbox** whose `$HOME` is
`/home/joshua/snap/claude-code/common`, *not* `/home/joshua`. Consequences:

- `~` in an agent shell resolves to the sandbox, so `git config --global` from the agent writes to
  the wrong file. Global config changes must be made by the user.
- The snap `home` interface grants **non-hidden** paths in `/home/joshua` and excludes dotfiles.
  That is the whole rule, and it explains everything below: `~/Documents` and `~/wpilib` are
  readable *and writable*, while `~/.gradle`, `~/.config` and `~/.ssh` are not. It is not a
  file-mode problem and `chmod` will not fix it; relocating out of the dotfile will.
- `/home/joshua/.ssh` is unreadable, so the agent cannot push. **The user pushes.**

**THE AGENT CAN RUN GRADLE.** This section previously said it could not, and that was true until
the Gradle cache was copied out of the dotfile:

```bash
cp -a /home/joshua/.gradle /home/joshua/gradle-home
rm -rf /home/joshua/gradle-home/daemon
```

Always invoke it as:

```bash
export JAVA_HOME=/home/joshua/wpilib/2026/jdk
./gradlew -g /home/joshua/gradle-home --offline <task>
```

`build`, `test` and `spotlessApply` all work, in a few seconds once the daemon is warm. The copy
leaves `~/.gradle` untouched, so the user's own VS Code builds are unaffected, and backing it out is
`rm -rf /home/joshua/gradle-home`. **Do not claim code is unverified for want of a build — run it.**

**The WPILib JDK is at `/home/joshua/wpilib/2026/jdk`** and *is* readable. Setting
`JAVA_HOME` to it lets the agent run `javac` directly. That was the only verification available
before the Gradle cache was relocated; it is now a fallback, and a weak one — see section 4.

**WPILib's own jars are readable** at `/home/joshua/wpilib/2026/maven`, including JUnit 5.10.1. That
is enough to compile and run pure-logic unit tests outside Gradle. It is *not* enough to run
anything that touches `Constants`, because `Constants.currentMode` calls `RobotBase.isReal()`, which
loads the `wpiHal` native — and that native is not in the offline repo.

**The GitHub repo is private.** Clone new working directories from a local sibling directory rather
than from GitHub; a non-interactive shell cannot answer the credential prompt.

**The agent cannot signal processes outside its sandbox.** `kill` returns "Permission denied" even
for the user's own PIDs, and `ss` is blocked as well, so the agent can list processes but cannot
stop them or inspect listening sockets. `./gradlew --stop` is the exception that works, because it
talks to the Gradle daemons over a socket rather than by signal — and stopping a daemon also kills
the simulation it forked. Note that typing a command with the `!` prefix in Claude Code does **not**
get around this: that runs in the same sandbox.

**`./gradlew simulateJava` launches no GUI.** `build.gradle` sets
`wpi.sim.addGui().defaultEnabled = false`, which the AdvantageKit template does on purpose, since
log replay requires every HAL sim extension to be disabled. Use VS Code's
*WPILib: Simulate Robot Code* command and tick the extensions you want. Do not flip that flag to
true — it would break replay, which is the reason this project uses AdvantageKit at all.

**`bin/` is the VS Code language server's output and is not what Gradle runs.** If robot code dies
with `java.lang.Error: Unresolved compilation problem` while `./gradlew build` passes, the IDE's
class output is stale or broken and something launched from `bin/` rather than
`build/classes/java/main`; that error string is an Eclipse JDT construct and `javac` never emits it.
Delete `bin/` — it is gitignored and regenerates. The specific cause of this, now fixed on `main`,
was `.vscode/settings.json` shipping with `java.import.gradle.annotationProcessing.enabled` set to
false: AdvantageKit's `@AutoLog` is an annotation processor, so with it off the language server
never generates the `XxxIOInputsAutoLogged` types and poisons every class that references one.

**AdvantageScope is read-only until you turn tuning mode on.** Values under `/Tuning` appear only
when the live source is *NetworkTables 4 (AdvantageKit)*, as a top-level `Tuning` table rather than
under `AdvantageKit/`, and editing needs the slider icon right of the search bar — purple means
active. Booleans then get a red/green circle to click. Any NT-writing dashboard works too; the Sim
GUI's own NetworkTables window is the quickest.

## 4. Verification expectations

This project treats verification claims as falsifiable, not rhetorical.

- "It compiles" means a build was actually run. If the agent could not run it, the agent says so and
  asks the user to run it.
- **"Tests pass" is weak evidence on its own** when the same author wrote the code and the tests.
  The M3 suite was validated by **mutation testing**: 13 deliberate defects were injected one at a
  time and each was confirmed to break a test. The first pass caught only 9 of 13; the four
  survivors were test gaps (not implementation bugs) and four tests were added to close them.
  Final score 13/13. Apply the same standard to future test suites.
- **Run the tests.** `PROJECT_OVERVIEW.md`'s "Testing standard" section is the authority: every
  mechanism gets an FSM suite over its `XxxIOSim`, and a suite counts as proof only once it has
  been shown capable of failing, by mutation testing and by permanent deliberate-failure cases.
  That section also lists the vacuous-pass shapes already found in this codebase; read it before
  writing a test, because four of the five were live in committed code.
- A known trap in this codebase's tooling: a `javac` run without the vendor jars produces hundreds
  of `cannot find symbol` errors, and filtering all of them hides *genuine* missing symbols in our
  own code. Filter by symbol name against known vendor types instead. This is how two undeclared
  `Constants.FloorRoller` members reached a commit.
- **`javac` parse-checking cannot see collisions with an unresolvable supertype.** With the vendor
  jars missing, `SubsystemBase` does not resolve, so javac never learns what it declares: a
  `private void idle()` clashing with WPILib 2026's `Subsystem.idle()` parsed cleanly and failed
  the real build. Overridden signatures, narrowed access and clashing generics are all invisible
  that way. Now that Gradle runs, this matters only if someone falls back to javac.
- Another trap, hit three times: scripted `str.replace()` edits **silently do nothing** when the
  anchor text does not match. Always verify an edit landed rather than trusting the script's exit.

- Field dimensions and goal coordinates are still `0.0`. Alliance flipping and distance-to-goal are

- `GeomUtil.interpolate`, `radialComponent`, `rotateAboutZ` and `toPose3d` have no test coverage.
  `rotateAboutZ` is the one the plan singles out as the classic vision bug; it lands in M8.
